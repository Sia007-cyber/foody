# 🍔 Foody — پلتفرم سفارش غذا و رزرو کافه/رستوران

پلتفرم Foody یک سیستم سفارش غذا و مدیریت کسب‌وکارهای غذایی (کافه/رستوران/فست‌فود) است که از سه پنل **مشتری**، **کسب‌وکار** و **ادمین** پشتیبانی می‌کند. سفارش غذا دو روش تحویل **Pickup** و **Delivery** دارد؛ رزرو میز مستقل از سفارش است و `DINE_IN` فعلاً نوع سفارش بک‌اند نیست.

> تیک‌ها نشان‌دهندهٔ وجود پیاده‌سازی در کد فعلی هستند، نه تضمین آمادگی production یا انتشار روی سرویس زنده. محدودیت‌ها و کارهای باقی‌مانده در بخش‌های زیر مشخص شده‌اند.

## وضعیت فعلی و اصلاحات پس از ممیزی — ۲۰۲۶-۰۹-۰۶

ممیزی کد انجام شده و ادامهٔ توسعه با حفظ Spring Boot Modular Monolith و React/Vite، به‌صورت تغییرات کوچک و مستقل پیش می‌رود. پایه‌های فاز ۱ و بخشی از فاز ۲ موجودند، اما قبل از گسترش قابلیت‌ها باید مشکلات P0 رفع شوند.

### اصلاحات امنیتی انجام‌شده

- [x] **رد حساب معلق در access و refresh:** وضعیت فعلی کاربر از دیتابیس بررسی می‌شود. توکن صادرشده پیش از تعلیق دیگر درخواست محافظت‌شده را احراز هویت نمی‌کند و refresh حساب معلق هیچ توکن جدیدی صادر نمی‌کند.
- [x] **کاربر حذف‌شده:** access و refresh با خطای احراز هویت `401` رد می‌شوند؛ مسیر access زمینهٔ امنیتی احرازشده ایجاد نمی‌کند.
- [x] تست‌های زنجیرهٔ واقعی Spring Security برای `CUSTOMER`، `BUSINESS_OWNER` و `ADMIN`؛ ادامهٔ کار حساب فعال و ممنوعیت استفاده از refresh به‌جای access نیز بررسی شده است.
- [x] **حذف افشای اطلاعات رزرو از API عمومی:** DTO مستقل `ReservationAvailabilityResponse` جایگزین لیست رکوردهای رزرو شده؛ هیچ شناسه، زمان رزرو، تعداد مهمان، وضعیت رکورد یا اطلاعات مشتری در پاسخ عمومی نیست.
- [x] تست یکپارچهٔ حریم خصوصی با MySQL واقعی؛ دسترسی جزئیات و عملیات مشتری/مالک مجاز حفظ شده و دسترسی مشتری یا مالک نامرتبط رد می‌شود.

اصلاح احراز هویت در commit `a65e29c` ثبت شده است. اصلاح حریم خصوصی رزرو در کد فعلی پیاده‌سازی و تست شده؛ انتشار این اصلاحات روی سرویس زنده در این بررسی تأیید نشده است.

### قرارداد عمومی رزرو

مسیر قبلی حفظ شده است:

```http
GET /api/businesses/{id}/reservation-availability?date=2026-09-06
```

پاسخ برای کسب‌وکار تأییدشده:

```json
{
  "date": "2026-09-06",
  "availabilityCalculated": false
}
```

`date` تکرار تاریخ درخواست است. `availabilityCalculated: false` یعنی ظرفیت/بازهٔ آزاد محاسبه نشده؛ **به معنی پر بودن یا آزاد بودن نیست**. این مسیر دیگر رکوردهای رزرو را نمی‌خواند و برای کسب‌وکار ناموجود یا تأییدنشده همچنان `404` برمی‌گرداند. شکل پاسخ از آرایه به این شیء تغییر کرده است؛ wrapper فرانت‌اند هماهنگ شده و هیچ صفحه‌ای مصرف‌کنندهٔ آن نبود. DTO جزئیات مشتری و مالک تغییر نکرده است.

هنوز ظرفیت‌سنجی، تخصیص میز، محاسبهٔ واقعی slot و اعتبارسنجی ساعات کاری نداریم.

### آخرین اعتبارسنجی

نتایج زیر مربوط به آخرین اجرای کامل پس از افزودن حفاظت همزمانی چرخهٔ سفارش و رزرو هستند.

| دستور | نتیجهٔ آخرین اجرا |
|---|---|
| `cd foody-backend && mvn test` | ۲۰۰ تست، بدون failure/error/skip؛ شامل رقابت‌های همزمان با Testcontainers و MySQL 8.4 |
| `cd foody-frontend && npm run build` | موفق |
| `git diff --check` | موفق |

تست‌های جدید شامل ۱۲ حالت پارامتری احراز هویت، ۳ تست واحد عدم صدور توکن و ۹ حالت یکپارچهٔ حریم خصوصی/مالکیت رزرو هستند. تست‌های standalone کنترلر جایگزین تست زنجیرهٔ واقعی امنیت نیستند. تست اختصاصی کیف پول هنوز اضافه نشده است. فرانت‌اند اکنون تست‌های خودکار نشست/API با runner داخلی Node دارد؛ این تست‌ها شامل مرورگر یا بک‌اند زنده نیستند.

### محدودیت‌های احراز هویت که هنوز باقی‌اند

- logout هنوز ابطال سمت سرور ندارد.
- refresh توکن‌های قبلی را باطل نمی‌کند؛ rotation امن و تشخیص استفادهٔ مجدد پیاده‌سازی نشده‌اند.
- تغییر رمز عبور ممکن است نشست‌های موجود را بی‌اعتبار نکند.

### نقشهٔ راه پس از ممیزی

این فهرست برنامهٔ پیشنهادی ادامهٔ کار است؛ موارد بدون تیک هنوز انجام نشده‌اند. هر مورد در یک تسک مستقل اجرا می‌شود.

## 🧱 تکنولوژی‌ها

- **Backend:** Spring Boot (Modular Monolith) + Maven + Java 21
- **Auth:** Spring Security + JWT (Access + Refresh Token)
- **Database:** MySQL + Flyway Migrations
- **Frontend:** React + Vite + TypeScript + React Router + TanStack Query — طراحی سبک اپل (Vazirmatn، RTL)
- **تست:** JUnit + Mockito (Unit) + MockMvc (Controller) + Testcontainers (Integration)

## 🔒 تصمیمات قفل‌شده‌ی اسکوپ

- پرداخت آنلاین → خارج از فاز ۱ (پرداخت حضوری/هنگام تحویل در اسکوپ است؛ `PAY_ON_DELIVERY` / `PAY_AT_COUNTER` هنوز فیلد یا enum پیاده‌سازی‌شدهٔ سفارش نیستند)
- مدیریت پیک/ناوگان تحویل → کلاً خارج از اسکوپ Foody (فقط ثبت سفارش با نوع `DELIVERY`)
- رزرو میز و سفارش غذا → در فاز ۱ کاملاً مستقل از هم هستن

## 🔮 فاز ۲ — کیف پول و درگیرسازی مشتری (بخشی موجود؛ ادامه پس از رفع P0)

> ترتیب فازهای این README جایگزین ترتیب قدیمی بخش «فازهای بعدی» در `foody-phase0-phase1-spec.md` است؛ تصمیمات معماری و استقلال سفارش/رزرو حفظ می‌شوند.
>
> جهت محصولی جدید بر اساس یک رفرنس UI که برای پروژه خواسته شده (اپ‌محور،
> کیف پول در مرکز، اعتبار/ماموریت، اسکن QR). **رقابت/لیدربورد کافه‌ها عمداً
> از اسکوپ فعلی حذف شده** — شاید بعداً، نه الان.
>
> صفحه‌ی هوم مشتری طبق موکاپ کارفرما بازطراحی می‌شه: هدر (لوکیشن + اعلان +
> آواتار)، کارت کیف پول/اعتبار + بنر تخفیف اپ، ردیف اکشن‌های سریع (اسکن QR
> میز، رزرو میز، شارژ کیف پول، پیشنهادها)، بنر پروموشن، لیست کافه‌های نزدیک
> (با تصویر/تخفیف/امتیاز/فاصله)، و بخش «ماموریت‌های امروز».
> ⚠️ کیف پول یعنی فقط **شارژ دستی/داخلی** (بدون درگاه پرداخت واقعی — طبق
> تصمیم قفل‌شده‌ی فاز ۱)؛ اتصال درگاه واقعی هنوز فاز ۳ هست.

## 🌐 دیپلوی تست (Live Demo)

طبق مستندات قبلی، دموی پروژه روی سرویس‌های زیر دیپلوی شده است. دسترس‌پذیری فعلی و نسخهٔ منتشرشده در این دور از اصلاحات بررسی نشده‌اند:

| بخش | سرویس | آدرس |
|---|---|---|
| بک‌اند | Render (Docker Web Service) | `https://foody-n39r.onrender.com` |
| فرانت‌اند | Vercel | `https://foody-eight-tau.vercel.app` |
| دیتابیس | Aiven (MySQL 8، پلن Free) | فقط داخلی، از طریق env vars |

**نکات مهم زیرساخت:**
- Render به‌صورت native فقط PostgreSQL/Redis می‌ده، نه MySQL — به همین خاطر دیتابیس روی **Aiven** (فری‌تایر همیشگی، بدون کارت اعتباری) میزبانی شده و از طریق `DB_HOST`/`DB_PORT`/`DB_NAME`/`DB_USERNAME`/`DB_PASSWORD` در Render وصل می‌شه.
- پروفایل Spring روی Render باید `SPRING_PROFILES_ACTIVE=prod` باشه (پروفایل جدید `prod` در `application.yml` که مقادیرش کاملاً از env میاد، شامل `sslMode=REQUIRED` چون Aiven اتصال رمزنگاری‌شده اجباری می‌کنه).
- `server.port` و `foody.jwt.secret` از env می‌خوانند (`PORT`, `FOODY_JWT_SECRET`)؛ کلید JWT هنوز fallback عمومی دارد و الزام کلید امن production یک کار P0 باقی‌مانده است.
- `FOODY_CORS_ALLOWED_ORIGINS` روی Render باید دقیقاً برابر آدرس ثابت Vercel باشه (نه آدرس هر deployment جدا).
- آپلود فایل فعلاً روی دیسک محلی سرویس ذخیره می‌شه (`FOODY_UPLOAD_DIR`) که روی Render **پرسیستنت نیست** — برای این تست مشکلی نداره، ولی اگه مشتری عکس آپلود کنه ممکنه بعد از ری‌استارت سرویس از بین بره. راه‌حل بلندمدت: Render Persistent Disk یا S3-compatible storage (فاز ۲).
- Render پلن Free بعد از مدتی بی‌فعالیتی sleep می‌ره؛ اولین درخواست بعدش چند ثانیه کند خواهد بود.
- هر `git push` به `main` هر دو سرویس رو خودکار دوباره دیپلوی می‌کنه (Render فقط اگه تغییر داخل `foody-backend/` باشه؛ Vercel برای هر تغییری، مگر Ignored Build Step تنظیم بشه).

راهنمای هر بخش: [بک‌اند](foody-backend/README.md) · [فرانت‌اند](foody-frontend/README.md).

## 🚀 اجرا (Backend)

بک‌اند به یه MySQL واقعی نیاز داره. دو راه:

**با Testcontainers** (نیاز به Docker، پروفایل پیش‌فرض `tc` — فقط برای `mvn test`، نه برای اجرای واقعی اپ):
```bash
cd foody-backend
mvn test
```

**با MySQL محلی/داکر** (برای اجرای واقعی `spring-boot:run`، پروفایل `local`):
```bash
# یک بار: یه MySQL بساز (اگه پورت 3306 قبلاً اشغاله، پورت دیگه‌ای مثل 3309 بگیر)
docker run -d --name foody-mysql \
  -e MYSQL_ROOT_PASSWORD=root -e MYSQL_DATABASE=foody \
  -e MYSQL_USER=foody -e MYSQL_PASSWORD=foody \
  -p 3309:3306 mysql:8.4

cd foody-backend
SPRING_PROFILES_ACTIVE=local \
SPRING_DATASOURCE_URL="jdbc:mysql://localhost:3309/foody?createDatabaseIfNotExist=true&serverTimezone=UTC&useUnicode=true&characterEncoding=utf8" \
mvn spring-boot:run
```
روی `http://localhost:8080` بالا میاد. Flyway خودکار همه‌ی migration‌ها رو اجرا می‌کنه
(شامل seed اکانت owner و admin — پایین رو ببین).

|---|---|---|

| Admin | `admin@foody.test` | `password123` |
