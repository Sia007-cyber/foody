# Production deployment

## Vercel frontend

- Root directory: `foody-frontend`; framework: Vite; install: `npm ci`; build: `npm run build`; output: `dist`.
- Use Node 22.12+ or a supported newer release.
- Set `VITE_API_BASE_URL=https://<backend-host>` before building, for each deployed environment.
  Supply only the origin, without `/api`, query parameters, or credentials. Never put secrets in `VITE_*`.
- Missing/HTTP/localhost API origins fail the production build. Changing the variable requires rebuilding.
- `vercel.json` rewrites SPA routes to `index.html`, allowing direct links and page refreshes.

## Render backend and Aiven MySQL

Root directory and Docker context: `foody-backend`; Dockerfile: `Dockerfile`.
The image builds and runs on Java 21, defaults to `prod` and UTC, and honors Render's `PORT`.
Set these environment variables explicitly:

| Variable | Value |
|---|---|
| `SPRING_PROFILES_ACTIVE` | `prod`; do not combine with `local` or `tc` |
| `DB_HOST` | Aiven service hostname matching its certificate |
| `DB_PORT` | Aiven service port |
| `DB_NAME` | Existing application database |
| `DB_USERNAME`, `DB_PASSWORD` | Database credentials with migration DDL and runtime DML permissions |
| `FOODY_JWT_SECRET` | Unique random Base64 secret decoding to at least 32 bytes; generate with `openssl rand -base64 32` |
| `FOODY_CORS_ALLOWED_ORIGINS` | Exact HTTPS frontend origins, comma-separated, no trailing slashes or wildcard |
| `FOODY_UPLOAD_DIR` | Absolute path inside an externally provisioned persistent mount |
| `FOODY_BUSINESS_TIME_ZONE` | Optional; defaults to `Asia/Tehran` for reservation validation |

The JDBC URL enforces `sslMode=VERIFY_IDENTITY`: encrypted transport, trusted certificate,
and matching hostname. Confirm the live Aiven certificate is trusted by the container JVM.
If its CA is private, import the Aiven project CA into a deployment-managed Java truststore
and configure `JAVA_TOOL_OPTIONS` with `-Djavax.net.ssl.trustStore=/path/to/truststore`
and the appropriate truststore password. Do not downgrade certificate verification.
The repository does not contain Aiven credentials or certificates, and local MySQL tests
cannot establish that live TLS configuration is correct.

The browser uses an explicit HTTPS API origin. No application-generated absolute redirects,
cookie auth, or request-scheme-dependent URLs currently require forwarded-header handling.
Uploaded image responses use relative `/uploads/...` paths; the frontend resolves them against the API origin.

There is no Actuator dependency: `/actuator/health` is not implemented, despite its security allowlist.
Use the existing public database-backed `GET /api/businesses` as the Render HTTP health-check path.
Verify it returns 200 after migrations and also verify authenticated flows on the deployed origins.

## Database release procedure

Back up the existing database before applying migrations. V1–V19 are ordered Flyway migrations;
Hibernate uses `validate`, not schema creation. Automatic baselining is disabled so an untracked,
nonempty schema cannot silently skip V1. Do not edit applied migrations or blindly repair checksums.
If an existing database is untracked, reconcile its schema/history before deployment.
V12 requires unique business owners; existing duplicates require a deliberate data reconciliation.
V13 preserves global wallets in read-only legacy tables; it does not assign their balances to businesses.

V19 suspends the known demo owner/admin and the demo owner's business, disables their passwords,
and revokes their refresh sessions without deleting history. It identifies them by original ID and email.
Inspect existing deployment data for renamed/copied demo accounts and any other fabricated content.

Before delivery, register a real account with a unique password and promote that exact verified
account to `ADMIN` using a trusted database administration session. Confirm its identity before the update,
set `public_id=NULL` for the non-customer role, then sign in again. Do not reactivate published demo credentials.
This is an operator task; no administrator password is committed or auto-generated by migrations.

## Uploaded images

Uploads are actively used by profile, business cover, and product forms. The implementation writes
only to local disk and serves the files publicly. Render's default filesystem loses those files on
replacement/redeployment. Setting an absolute path does not provision a persistent disk.

Before production, attach and back up a persistent Render disk mounted at `FOODY_UPLOAD_DIR`, or
choose and implement durable object storage in a separate authorized infrastructure task. No new
provider has been introduced. Copy any existing files that must survive into the durable store.
The current disk approach assumes one backend instance with that mount; it is not shared object storage.

## Before PWA/mobile

Complete the storage, administrator and live HTTPS/CORS/database verification above, then perform
customer/owner/admin browser acceptance on the deployed web app. No present SPA architecture issue
requires a redesign before PWA work. Offline behavior, private-data caching, installability, service
workers, push delivery, and native packaging require separate decisions and implementation.
