# Foody Frontend

رابط فارسی و RTL پروژهٔ Foody، شامل پنل‌های مشتری، مالک کسب‌وکار و ادمین. وضعیت کامل پروژه و اولویت‌های توسعه در [README اصلی](../README.md) آمده است؛ اصول ظاهری در [DESIGN.md](DESIGN.md) قرار دارند.

## فناوری‌ها

React 19، TypeScript، Vite، React Router و TanStack Query، با فونت Vazirmatn و Oxlint.

## اجرای محلی

دستورها را از پوشهٔ `foody-frontend` اجرا کنید:

```bash
npm install
cp .env.example .env
npm run dev
```

آدرس پیش‌فرض `http://localhost:5173` است. مقدار `VITE_API_BASE_URL` در `.env` به‌صورت پیش‌فرض `http://localhost:8080` است؛ بک‌اند باید جداگانه اجرا شود و CORS آن origin فرانت‌اند را بپذیرد.

## بررسی و ساخت

```bash
npm run build
npm run lint
npm test
```

`build` بررسی TypeScript و ساخت Vite را اجرا می‌کند. برای مشاهدهٔ خروجی ساخته‌شده از `npm run preview` استفاده کنید. تست‌های نشست و API با runner داخلی Node اجرا می‌شوند؛ وابستگی تست جدیدی اضافه نشده است. این تست‌ها با Node 26.8.1 بررسی شده‌اند و به پشتیبانی اجرای مستقیم TypeScript در Node نیاز دارند. جزئیات در [راهنمای تست نشست](tests/README.md) آمده است.

## ساختار

- `src/features/`: صفحات و APIهای هر قابلیت، از جمله سفارش، رزرو، کیف پول، اعلان، پروفایل و پنل‌ها
- `src/components/`: اجزای مشترک رابط و چیدمان
- `src/lib/`: کلاینت HTTP، Query Client و ابزارهای مشترک
- `src/types/`: قراردادهای مشترک TypeScript

## وضعیت فعلی

جریان‌های ورود/ثبت‌نام، کشف کسب‌وکار، منو، سبد خرید، سفارش، رزرو، اعلان، کیف پول و مدیریت کسب‌وکار پیاده‌سازی شده‌اند. کیف پول شارژ شبیه‌سازی‌شده دارد؛ پرداخت سفارش از کیف پول هنوز متصل نیست.

موارد مهم باقی‌مانده:

- هدایت پس از ثبت رزرو به `/reservations/:id` می‌رود که صفحه‌ای برایش تعریف نشده است.
- جزئیات لازم سفارش برای آماده‌سازی و ارسال در پنل مالک کامل نمایش داده نمی‌شوند.
- بخشی از اعتبار، تخفیف و آمار داشبورد نمایشی است؛ QR و پیشنهادها هنوز پیاده‌سازی نشده‌اند.

پاسخ عمومی availability رزرو شیء `{date, availabilityCalculated}` است. مقدار `false` یعنی ظرفیت محاسبه نشده؛ wrapper در `reservationApi.ts` هماهنگ شده و در حال حاضر هیچ صفحه‌ای آن را مصرف نمی‌کند.

## چرخهٔ نشست

`src/lib/session.ts` مرجع توکن‌ها، کاربر و نسل نشست است و `authSession.ts` ورود، ثبت‌نام، بازیابی و خروج را هماهنگ می‌کند. پیش از جایگزینی حساب، پروفایل با توکن جدید بررسی می‌شود؛ خطای موقت یک بار تکرار می‌شود و شکست نهایی نشست قبلی را حفظ می‌کند. اگر ثبت‌نام انجام شده اما دریافت پروفایل شکست بخورد، پیام فارسی کاربر را به ورود با حساب ساخته‌شده راهنمایی می‌کند.

در خروج، شکست refresh و بازیابی ناموفق، توکن‌ها و کاربر پاک می‌شوند، درخواست‌های نشست قبلی abort می‌شوند و کل QueryClient پاک می‌شود. در تعویض حساب هم همین پاک‌سازی پیش از نمایش حساب جدید انجام می‌شود. کلیدهای کاتالوگ عمومی و مالک هم‌پوشانی دارند؛ پاک‌سازی کامل انتخاب شده تا هیچ گروه خصوصی جا نماند. در نتیجه دادهٔ عمومی هم دوباره دریافت می‌شود. درخت رابط وابسته به نشست remount می‌شود؛ سبد خرید مستقل از حساب بیرون این مرز باقی می‌ماند تا ورود هنگام خرید آن را خالی نکند.

refresh در هر تب یک promise مشترک دارد؛ درخواست‌ها حداکثر یک بار تکرار می‌شوند. رخداد `storage` تغییر توکن در تب دیگر را تشخیص می‌دهد، کاربر/cache قبلی را کنار می‌گذارد و در صورت وجود اعتبارنامه، هویت جدید را از سرور می‌خواند. این سازوکار قفل refresh مشترک بین تب‌ها ایجاد نمی‌کند.

خطاهای JSON، خالی، متنی و JSON خراب همگی `ApiError` با status واقعی HTTP هستند؛ فیلدهای معتبر حفظ می‌شوند و در نبود پیام، متن فارسی شامل status استفاده می‌شود. upload نیز همین مسیر خطا و refresh را دارد.

ابطال logout در سرور، refresh rotation/تشخیص استفادهٔ مجدد و ابطال نشست پس از تغییر رمز همچنان خارج از این اصلاح هستند.
